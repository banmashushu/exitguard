# Proxy-first 独立验收

日期：2026-10-26。审查基线：`23e9723`；范围为本次 `proxy-first` 工作树差异及新增远程协议测试。角色：Astra 独立验收，仅审查与运行测试，不修改产品代码。

## 当前结论

截至本轮审查，未发现阻止按普通本机代理交付的功能或安全问题。代码与本地协议集成证据支持：ExitGuard 可以在没有 OS 过滤证明、没有安装 Claude 的情况下，启动仅回环监听的代理，并通过指定远程上游转发 HTTP 与 HTTPS CONNECT 流量。该结论不等于完整应用流量保护或真实第三方代理、Claude、Windows 的实机验收。

两位实现者收尾后已完成限定复审：读取最终交付报告，复核 TLS 取消、CONNECT 2xx、凭据与无效配置撤销、模式措辞和启动版本检查。没有新增未解决的普通代理交付阻塞项；后续整包构建与视觉检查由父窗口执行。

## 已核对的关键要求

- 迁移没有静默降级：仅缺失配置文件的新用户默认 `remote` / `proxy-only`；已保存配置或显式配置对象缺失 `enforcementMode` 时仍补为 `required`。严格模式继续要求真实且匹配的系统过滤证明。
- 代理模式独立可用：完整验证不要求已安装目标程序，`Check` / `Arm` / 健康检查只在明确 `required` 时读取 OS 证明；`proxy_ready` / `proxy_active` 保持 `FilterActive=false` 和空策略指纹。
- 凭据隔离：远程账户独立从受鉴权的 API 输入，仅保存在进程与当前路由内存；不会进入配置、状态、事件或代理 URL。修改上游端点或来源会先撤销会话、关闭连接，再清除远程账户。保留同一端点、只更新期望 IP 的保存不会误清账户，因此正常设置流程可连续完成。
- 协议失败关闭：HTTP(S) 使用 CONNECT 和可选 Basic；SOCKS5 只接受当前提供的认证方法，验证 RFC1929 回应及 CONNECT 回应。认证、TLS、截断、超时和上游不可达均无直连目标或协议降级分支。HTTPS 使用系统证书验证与原始主机名，TLS 成功前不发送账户；测试根证书注入为私有接口，无生产跳过验证开关。
- DNS 路径：只有上游代理自己的主机名可用系统解析，并在该路由固定 IPv4。目标名称通过所选上游上的 DoH 查询 A 记录；实际拨号仍只拨上游固定地址。拒绝自身监听递归、IPv6 目标及不支持的协议。
- 会话撤销：保存、凭据变更、暂停、验证失败均递增 `SessionRevision`，撤销待验证与健康检查，并关闭持有连接。启动 API 检查页面版本，命令准备与最终 `Start` 前再次检查当前版本、方式、状态和代理地址；旧版本请求以及暂停后重新启用的同策略会话不复用原启动资格。
- 界面和文档：可完成“保存服务器 → 提交账户 → 查看候选 IP → 手动填写期望 IP 并保存 → 检查 → 启动”流程。账户输入提交即清空；候选值不自动认可或启用。普通代理采用不同状态与颜色，并明确解释未核验系统防绕行；缺失 Claude 仅影响该启动入口。保留严格模式要求、可选 Mihomo 路径及现有系统规则可能仍生效的提示。

## 真实剩余边界

本轮没有使用或购买用户的第三方固定代理，没有登录 Claude，也没有修改飞连、系统代理、DNS、路由或 OS 过滤。真实代理兼容性、账户可用性、实际固定出口与当前 Claude 是否采用 Electron 参数仍待用户环境验证；交叉编译不等于 Windows 网络实机验证。

普通代理只约束实际经过它的 IPv4 TCP。绕过代理的代码、UDP 和其他窗口的直连不在这个模式的保障范围。IP 轮询存在检测窗口，不能保证两次检查之间上游 NAT 永不改变。HTTP/SOCKS5 到上游的链路本身不加密；HTTPS 正常验证证书。上述范围已经在设置、运行状态和 README 中说明。

严格模式原有的系统服务代发 DNS、更新新增辅助程序覆盖与平台签名部署缺口仍存在。这些不能被重新包装成“全局保护已完成”，但也不是本次普通代理转发交付的前置条件。
