# ExitGuard 双端固定出口守护：已确认设计

日期：2026-10-23。状态：用户已确认各端独立固定出口，并批准按双端强制断流版实施。系统网络变更尚未执行。

## 用户目标与已知环境

用户希望在 Windows 和当前 Mac 上保护 Claude 桌面端及浏览器的网络出口，减少意外直连、自动换节点和出口变化。不能把固定出口宣传为保证 Claude 不封号，也不处理账号实名认证。

- Windows 使用 Clash，暂时没有固定公网 IP 节点；具体客户端版本、端口和控制接口尚未确认。
- 当前 Mac 使用公司的飞连 VPN。用户称其为公司固定 VPN，但是否提供固定公网 IP、是否接管 Claude 流量尚待实测。
- Mac 已安装飞连 3.2.16，网络扩展处于启用状态；无法据此证明 VPN 已连接、处于全局模式或已接管指定进程。
- Mac 已安装 Chrome 和 Safari，尚未找到 Claude 桌面客户端。已有 Clash 配置属于历史信息，不作为当前运行配置。
- Mac 具备编译普通本地应用的工具；系统级 Network Extension 的签名、部署资格和 Windows 验证环境未确认。

用户已确认：两台电脑各自保持固定出口，不要求相同公网 IP。Mac 使用公司飞连，Windows 使用 Clash 指定节点；固定公网出口仍需各自的节点或网关提供。

## 产品行为

应用提供统一的出口配置、连接诊断、受保护入口和状态记录。用户首次设置出口来源、期望的 IPv4/IPv6 地址及需要保护的应用。未配置或未验证的出口保持“尚未就绪”，不能因一次公网 IP 探测成功自动认为所有 Claude 流量安全。

状态分别表达：

1. 未配置：缺少出口来源或固定 IP。
2. 检查中：正在识别路径和验证出口。
3. 仅监测：能够探测出口并提醒变化，但没有强制限制目标应用流量。
4. 代理路径已验证：指定浏览器/客户端的已验证网络路径经过固定代理；覆盖范围和未覆盖项单独记录。
5. 阻断已验证：只有系统层限制实际安装且通过断线测试，才允许显示此状态。
6. 已暂停或异常：出口不符、节点或隧道不可达、配置变化、探测失败、睡眠唤醒或路径变化需要重新验证。

“探测进程出口正常”“浏览器代理栈正常”“Claude 全部进程受约束”是三种不同证据，不互相替代。

## Windows：对接 Clash

使用用户已有的 Clash/Mihomo 本机控制接口。只访问明确配置的本机地址；控制密钥存于系统凭证存储。不同 Clash 客户端能力不同，必须先进行只读兼容性检查。

- 采用单一明确节点，拒绝自动测速、故障切换、负载均衡和隐含动态分组作为固定出口承诺。
- 有控制接口时读取并核对选中节点、节点链和运行状态。应用仅管理自己创建的专用策略，变更有备份，退出时只恢复自己仍拥有的设置。
- 保护配置优先使用专用本地监听入口，明确绑定目标节点，不能只读取一次全局节点选择后将其视为永远固定。
- 没有专用监听或可信节点绑定能力时，显示“仅监测”或“不支持当前配置”，不静默降级。
- 节点本身必须提供固定公网出口。第一次观察到某 IP 并不证明服务商保证固定；确认期望 IP 前不标为固定出口就绪。
- 如节点不支持 UDP，应在专用路径明确拒绝相应流量，防止规则继续匹配到直连。

浏览器优先采用专门的 Chrome/Edge 独立资料目录和显式单代理入口；不复用用户正在使用的普通浏览器进程，不写入全局系统代理。不得配置 DIRECT 回退。其可交付承诺先限定于实测覆盖的协议。

Claude 桌面端必须识别实际安装路径和辅助进程并验证真实连接行为；未经验证的 Electron 参数不能作为保护证据。Windows 系统级拦截需单独验证防火墙规则或流量过滤方案，不能使用“允许本地代理 + 阻止全部”这种会被阻止规则覆盖的错误配置。

## macOS：兼容公司飞连

保持飞连的配置和管理权限边界。应用不切换公司 VPN 模式、不读取公司凭证、不调用未经公开说明的私有 XPC 接口，不重写系统 DNS、默认路由或安装另一条 TUN 隧道。

官方资料区分全局模式和极速/分流模式，且存在智能选路。是否固定出口，需要结合实际路径、公司所提供的节点和管理员配置验证。

- 初始适配为只读识别和路径诊断。找不到可靠的状态来源时显示“未知”，不用 utun 编号、扩展已启用或无语义的状态数字推断飞连连接成功。
- 出口探测地址可配置，默认只传必要网络请求，不上传账户、聊天内容或设备文件。普通探测地址可能与 Claude 分流路径不同，诊断必须保留这一差异。
- 若公司提供允许使用的 HTTP/SOCKS 代理入口，可接入受保护的独立浏览器路径；需要验证入口是否稳定、是否允许目标服务和是否存在直连回退。
- 如果公司只有 VPN 路由，不提供代理入口，普通应用无法据此承诺对任意进程实现强制出口锁定。此时第一阶段只能交付监测与启动前检查，必须显示“仅监测”。
- 要实现 VPN 退出后仍强制阻断 Claude 和浏览器直连，需要兼容现有飞连的系统级网络过滤能力，可能涉及 Network Extension、有效签名、系统授权和公司允许的扩展部署。该能力属于必须单独验证的后续交付，不以监测或自动关闭应用替代。

## 统一异常策略

实施补充：Mac 严格过滤在无法安全识别某条出站 socket 流的进程时丢弃该流并报告异常，避免以身份查询失败作为放行理由。该保守处理可能影响少量无法归属的非目标流量，必须在安装前明确展示并完成兼容性测试；当前开发过程不安装过滤器。

出口 IP 不符、检查超时、节点变化、VPN 路径变化、睡眠唤醒或 Wi-Fi 切换后，状态立即转为未验证/暂停。对于应用拥有的代理入口，可停止接受新代理请求并关闭其拥有的连接；不得声称这样可阻断未被接管的进程。

检测周期存在时间窗口，因此不能保证公网出口变化后的首个请求就被截住。固定节点或网关自身的出口稳定性与本地断流保护是不同问题。

默认不强行关闭用户已经打开的普通浏览器或其他办公软件。任何系统级阻断只覆盖已确认的目标进程与路径；若某系统只能全设备断网，必须作为另一个明确选择，不能默认替换原需求。

## 技术方案与交付阶段

实施选择：Go 标准库网络核心与本地控制界面，macOS 提供轻量原生窗口，Windows 提供独立可执行程序与本机控制面板。按系统提供网络过滤适配器。现有 Go/Swift 工具链可构建，减少额外运行时依赖，并将网络核心与界面分别测试。界面只展示用户能理解的出口、状态、异常原因与下一步。

阶段一交付可运行的双端基础应用：配置保存、IP 检查、变化通知、事件记录、飞连只读适配、Clash 只读兼容性检查，以及在能力足够时启用经过验证的专用代理入口。Mac 只有监测能力时明确呈现，不能作为整个强制保护目标已完成。

阶段二交付强制保护：完成 Windows 与 macOS 的进程覆盖、系统阻断、IPv6/UDP/DNS边界验证及真实客户端测试。需要固定出口、目标客户端、平台构建测试环境以及系统授权和签名条件就绪。缺项不得用模拟测试当作真实通过。

## 验收要求

- 正常连接时，通过受保护浏览器和实际 Claude 桌面端验证出口；不能只验证应用自身的公网探测。
- 代理远端不可达、代理内核退出、管理应用退出、Clash 策略变化、VPN断开和恢复时，分别验证请求结果和是否发生直连。
- 睡眠唤醒、Wi-Fi切换、IPv4/IPv6、DNS、UDP/WebRTC、长连接、文件上传及辅助进程分别核验。
- Windows 必须在实际 Windows 环境完成关键网络验证；Mac构建成功不能代替。
- 系统网络变更必须可回滚；不留存密钥明文，不保存聊天请求内容，不安装 TLS 解密根证书。
- 确认公司飞连网络仍可正常使用。会主动断开 VPN 或影响办公连接的测试，必须安排在用户同意的测试时段。
