# Windows native preview

This integration launches Chrome, Edge and Claude on the existing Windows desktop, in separately installed Sandboxie Plus boxes. It uses no virtual machine and changes no system proxy, DNS, VPN or routing. Existing `proxy-only` and `required` modes retain their original semantics. Native preview never supplies the `enforce.Proof` used by required mode and never sets `armed` or `FilterActive`.

The initial supported runtime is official Sandboxie Plus **v1.18.8 x64**, shared core **5.73.8**, ABI `0x57230`. It is a separately installed dependency; vendor binaries, licenses and credentials are not bundled. The native package is built by `scripts/package-windows-native.sh`, with numbered Chinese entry points and a guide. Current development and checks ran on macOS; cross-compilation and local/mocked tests are not Windows validation.

## Runnable path

1. `native-template --output owned.ini` can generate the scoped fragment offline. It changes nothing and is not a runtime certificate.
2. On Windows, `native-stage --output plan.json` reads the actual runtime-selected INI and stages the three new product boxes with its current SHA-256. It refuses running target applications, existing product boxes, external includes and unreviewed global settings. It does not change any global or existing box.
3. After reviewing the exact plan, explicitly run `native-apply --plan plan.json` with sufficient rights. It requires `NetworkEnableWFP=y` already present, takes an exclusive file handle, checks the current digest, backs up the original into a file created with a protected DACL allowing only SYSTEM/Administrators/file owner before any content write, appends only the three new sections, reloads through the documented API and checks the resulting runtime. It never toggles WFP. A post-append reload/check failure is reported explicitly; it does not launch applications or repeatedly append.
4. `native-inspect` queries driver version and **effective** merged box/global/template values through `SbieApi_QueryConf`. It then reads actual BFE callouts and filters. Successful preconditions still return `preview-incomplete`.
5. Start `serve --native-console` using the package's protection-window entry point. Initially configure/enable the existing proxy on 127.0.0.1:17890 in the browser panel, then completely close Chrome/Edge/Claude, including the browser hosting configuration. Keep the separate numbered protection console open: it launches all three applications independently and can pause/recheck/resume without a browser. It calls the same live service in process, never transfers a token through a file/command line, and suppresses the normal ready JSON. Reopening configuration first requires all three target basenames stopped. An authenticated panel API remains an alternate entry for a control browser other than the selected target; it cannot exempt an existing target instance. The service checks the current session revision, prepares the verified `Start.exe /box:ExitGuard_*` command, rechecks the session under the service lock and starts it without a shell or direct-launch fallback. Pausing or changing the session during preparation cancels the launch.
6. The separate shipped `ExitGuardNativeProbe.exe` can be invoked through `native-probe --target chrome|edge|claude`. It observes its actual box and process flags, probes the explicit HTTP proxy, direct IPv4/IPv6, other loopback ports, UDP, `GetAddrInfoW` and `DnsQueryEx`, and repeats in a newly renamed descendant. Output always remains `incomplete`. A separate host-controls mode requires a definitive unboxed query for its own live PID before opening local echo/control listeners; unknown signature/API errors stop it. Receivers log actual TCP/UDP counts, peers and byte counts, with the UDP client local endpoint for correlation. The operator must also verify the positive controls are reachable. Neither report files nor booleans can be imported to grant protection.

Only newly boxed processes from the explicit preview entry are in scope. Ordinary shortcuts and existing unboxed processes are not automatically captured. All existing processes with the target basename block preview launch; ExitGuard does not kill them. Each target uses a separate profile path that remains virtualized inside its product box. No existing user profile is opened through a direct-access exception. Real login, storage, upload and update compatibility remains unverified. The owned policy explicitly rejects software updaters, so updates may fail in the box and require separate review/testing.

## Effective policy and source decisions

The owned policy sets `AllowNetworkAccess=y`, `PromptForInternetAccess=n`, `BlockLocalLoop=n`, broad `NetworkAccess=*,Block` and only `*,Allow;Address=127.0.0.1;Port=17890;Protocol=TCP`. The exact closed IPC path is `\RPC Control\DNSResolver`; `UseRuleSpecificity=n` is explicit. Normal DNS for proxied websites is handled through ExitGuard's existing upstream resolver. These configuration statements are prerequisites, **not proof** of actual DNS broker containment.

The runtime verifier enumerates keys from the box and `GlobalSettings`, then queries every effective value with globals/templates still enabled. It uses `CONF_GET_NO_EXPAND` solely to compare the literal, pinned `%SystemRoot%` template values consistently. Arbitrary extra keys/values, external network allows, breakout triggers, host injection and relaxed isolation fail closed. There is no invented `DisableInheritance` option or ineffective `BreakoutDocumentProcess=...,n` shadow.

Stock Sandboxie merges `[DefaultTemplates]` into global runtime policy even when a box specifies no `Template`. The reviewed v1.18.8 `Templates.ini` baseline is pinned in `internal/nativeapp/data/sandboxie-defaults-5.73.8.json` (Git blob `aa2453a0eef7fa9b4ae797479dfe7c6c1e1c953a`), containing 15 keys/100 values. Only those exact baseline values are allowed in addition to the owned settings. The two stock `OpenIpcPath` patterns concern webcache and do not match `DNSResolver`; broad/additional IPC values are rejected.

The exact stock `BreakoutDocumentProcess=explorer.exe,y` selector is allowed only while every effective `BreakoutDocument`, `BreakoutProcess` and `BreakoutFolder` trigger is absent. Source `core/dll/sh.c` requires a separate matching `BreakoutDocument` before invoking host execution. A regression adds inherited `*.pdf` and must reject the policy. Exact stock `SoftwareUpdater` values are a deny classification: `core/dll/proc.c` returns access denied for a matching updater when `BlockSoftwareUpdaters=y`; this setting is explicit in each owned box. Unknown custom configurations stop with the key name and preserve existing vendor settings.

Four current registered kernel callouts are required, for IPv4/IPv6 `ALE_AUTH_CONNECT` and `ALE_AUTH_RECV_ACCEPT`, with their exact source GUIDs. Each must have one unconditional dynamic terminating-callout filter in Sandboxie's sublayer, weight UINT8 15 and no provider. Extra/conditional/missing filters, absent kernel `FWPM_CALLOUT_FLAG_REGISTERED` or API query failures reject preview. Merely setting the driver feature flag would be insufficient: Sandboxie sets intent before completing registration.

File discovery uses the installed HKLM service path, exact reviewed publishers/versions, local regular paths without reparse points and safe DLL loading. Official signed core identities were read without executing the files from the same-release Classic core installer: NOVASYNC LABS PTE. LTD. for Start/SbieDll/SbieSvc and Microsoft Windows Hardware Compatibility Publisher for SbieDrv. Plus installer has the same NOVASYNC identity; Plus inner files were not independently extracted. Exact leaf certificate thumbprints are pinned as well. Windows must still report `Get-AuthenticodeSignature` **Valid** for each installed file before any vendor DLL is loaded. Unknown signers are surfaced in `native-inspect`, never silently accepted. Application executables require matching filenames and their publisher signatures. New versions or changed signatures require revalidation.

## Verification still required on actual Windows

The implementation has not been executed on Windows. The required acceptance record includes installed signature chain/version, actual four BFE registrations, effective template policy, parent and newly named child attribution, other-loopback/IPv4/IPv6/UDP negatives with live positive controls, explicit proxy positive control, and simultaneous broker/physical-interface/controlled authoritative DNS observation for `GetAddrInfoW` and `DnsQueryEx`. DNS errors, NXDOMAIN and connection failures alone do not establish blocking.

Also test proxy pause/crash, upstream authentication/availability failure, unaffected ordinary application networking, and Chrome/Edge/Claude login, upload, profile persistence, restart and update behavior. IPv6 and UDP are deliberately denied; realtime features may be affected. Missing evidence keeps the native integration incomplete. There is no automatic armed promotion, report import, claim of absolute anti-ban protection or guarantee that the upstream provider supplies static egress.
